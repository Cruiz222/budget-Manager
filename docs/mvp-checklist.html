  • Built, and the fourth answer turned out to be the one that mattered. The three options here — hold it, reverse it, accept it — are all about money already paid. There is a fourth: refuse earlier, where _prepare already refuses, on its own stated thread that every refusal here costs nobody anything. Because the cap was not actually being enforced there against more than one request. The defect: the daily outflow cap counted PENDING rows, in the port's own words — "a cap that ignored held money would let a burst of in-flight payouts each pass on its own" — and the balance cap had no equivalent on the incoming side. So a burst of deposits each read the same untouched balance, each fit under the ceiling, and all of them settled: the same bypass, closed on the other side of the ledger. This is the ceiling whose argument is anti-mule rather than convenience, so passing it by asking twice was passing the control that matters most. The fix is the incoming mirror of the read that already existed: pending_credit_total(wallet_id, currency) sums PENDING DEPOSIT rows with no time window — a pending collection has no day, and one waiting across midnight is precisely the row that most needs counting — implemented in both adapters and summed in Python Decimal over a selected column, never SELECT SUM(), because amounts are stored as TEXT and SQLite coerces a text operand to REAL, so a hundred addends of 0.10 come back as 9.999999999999998. That hazard lands here in the same place as the outflow total and worse: this number is compared against the ceiling with >, so a hair under admits a deposit a hair over it. A second change fell out of the first: the dedupe check now runs before the ceiling in _prepare, because a client retrying a key that is still open would otherwise have its own amount counted twice and be refused for a breach that existed only because the retry was counted — answering "this account may not hold that much" to somebody who asked once and lost the response. The residual, stated rather than left to be discovered: two genuinely simultaneous requests can still both pass, because the PENDING row is written after initialize_deposit returns and not before — deliberately, since holding a write transaction across a third party's response time is an outage proportional to theirs. Closing that means reserving at intent time, which reverses a documented decision. So the settlement side is where the residue is answered: a credit that breaches the cap is applied and the crossing is named, SettlementOutcome.BALANCE_CAP_EXCEEDED, carried by the webhook's own log line and response body and counted by the reconciler. Accepting silently was the one answer not available — refusing would park the payer's money at Paystack with no automated path back, PaymentProvider having no transfer method, and a row left PENDING over money that has arrived would be a lie the reconciler repeats for ever. The pre-existing suite was green on both runs, which is the part that matters most — nothing in this tree turned out to be relying on being able to knock on a door without limit.

The browser client’s first run found two defects, and both were in the code rather than in the tests. It came back 71 failed, 3,311 passed, 7 errors, and the failures were two shapes rather than seventy-one things. Every page this layer renders on a failure was served 200 OK. templating.render had never passed a status to starlette’s TemplateResponse, and errors.Browser put the grade in the template context only — so a 404 page answered success to a browser that would cache it, a search engine that would index it and an uptime check that would believe it, the number in the body being invisible to all three. And the suite was following redirects. Its own conftest argued at length that it must not, because a client that follows a 303 turns “the form redirected to the confirmation page” into “the confirmation page rendered” — a weaker claim about a money operation — but follow_redirects=False had never been written, and TestClient’s default is the opposite. Every test written against that paragraph had been asserting on the page at the far end of a redirect, which is why the failures read as templates where statuses were expected. Both were fixed at the boundary that was wrong — render gained a status_code defaulting to 200, and the flag is now spelled at all five construction sites — and the run above is the re-run: 3,391 passed, nothing failed, in 374.70s. Which is the argument for the plan’s verification section rather than for the reviewer: a missing keyword argument and a default left un-overridden are both invisible to a reader, and neither was found by reading.

And one product rule changed after that run, so the count above is one rule out of date. A person may now hold one wallet per currency, and the currency list is NGN and USD — decision 267, taken because two wallets of one currency split a balance the person cannot add up themselves. Three of the five currencies are gone from Currency rather than hidden behind a policy list, so the web dropdown, the CLI’s choices and the 400’s own message all narrowed without being edited; six rows left tier.py’s limits table with them, which is the completeness test doing its job rather than a coincidence. No item on this page moves, because no item here was about currencies. What the change does carry is a migration: a database that already holds a GHS wallet, or that holds the two same-currency wallets this rule exists to stop, is dealt with on the next open — resolved and printed if the row is provably empty, refused by name if it holds money, because re-denominating money is not something this system does by itself. The suite has not been re-run against this yet, so the honest headline for that change is a revision and a number still owed rather than one added here.
